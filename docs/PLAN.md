# 历史军事行动动态地图 · 规划与设计

> 状态：规划 v0.2　·　六项关键决策已确认，见文末 §15；M0 脚手架与 M1 引擎已完成。
> 文中以诺曼底举例的部分为最初的规划草稿，首个实际战役已改为**四渡赤水**（§15）。

---

## 1. 项目定位

**一句话**：把历史上真实发生的军事行动，在地图上按时间"演"出来——部队移动、战线推进、关键战斗依次发生，并配有可查证的来源说明。

**不是什么**：

- 不是战争游戏或战术模拟（不做"如果……会怎样"）。
- 不是百科全文（叙述保持精炼，细节靠来源链接）。

**核心体验**：

1. 选一场战役 → 地图飞到战场 → 点播放。
2. 时间轴推进，各方部队沿真实路线移动，战线区域随时间变化，事件弹出说明。
3. 可暂停、拖动时间轴、切换速度、点击任一单位或事件查看详情与出处。
4. 可以分享"某一时刻的某个视角"的链接。

## 2. 关键判断：难点在数据，不在前端

地图渲染、时间轴、动画都是成熟技术，一两周就能做出能跑的原型。真正决定项目成败的是：

| 挑战                                                   | 影响                             | 设计对策                                                                     |
| ------------------------------------------------------ | -------------------------------- | ---------------------------------------------------------------------------- |
| 史料本身不精确（古代战役常只有"某年某月"，路线靠推测） | 动画会给人"精确"的错觉，产生误导 | 每个数据点带 **时间精度** 和 **可信度**，界面上用实线/虚线区分（见 §6、§10） |
| 每场战役都要人工研究、标注坐标和时间                   | 内容产出是瓶颈                   | 数据用 **文本文件 + Git 管理**，后期提供编辑器降低录入成本                   |
| 古今地名、边界、海岸线不同                             | 底图与史实不符                   | 底图只作地形参照，历史地名/边界用自有图层叠加                                |
| 敏感战争的叙述立场                                     | 争议、误导                       | 制定中立性与来源规范（§10）                                                  |

因此规划的重心是：**先把数据模型和"史实可信度表达"设计好，再选技术**。

## 3. 目标用户与场景

- **历史爱好者 / 学生**：想直观看懂一场战役的来龙去脉（主要用户）。
- **教师**：课堂演示，需要稳定、可离线、全屏友好。
- **内容贡献者**（后期）：想补充/纠正某场战役的数据。

首选场景：桌面浏览器演示；移动端可用但不作为第一优先。

## 4. 功能规划

### MVP（第一个可发布版本）

- 战役列表首页（卡片：名称、年代、一句话简介、缩略图）。
- 战役播放页：
  - 地图 + 播放/暂停/倒退/倍速 + 可拖动时间轴。
  - 部队图标沿路径移动，带尾迹。
  - 战线 / 控制区域随时间变化。
  - 进攻/撤退箭头。
  - 事件标记：到达时间点自动弹出说明卡片。
  - 图层开关（按阵营、按类型）。
  - 单位详情面板：名称、编制、兵力、指挥官、出处。
- **章节（Chapter）叙事**：把战役拆成几个阶段，每段有文字说明、镜头位置、播放速度。
- 数据可信度可视化（实线=有据可查，虚线=推测）。
- 中英双语数据结构（界面先做中文，数据字段从一开始就是多语言）。
- URL 状态同步：`/#/c/normandy-1944?t=1944-06-06T06:30&lat=..&lng=..&z=..`。
- 纯静态部署，无后端。

### 第二阶段

- 历史疆域/边界叠加层（按年代切换）。
- 兵力/伤亡随时间变化的小图表。
- 序列战斗（Order of Battle）树状面板。
- 3D 地形与山体阴影；羊皮纸/古地图风格底图。
- 移动端适配打磨、图片/史料图片展示。
- 每场战役的"来源与延伸阅读"页。

### 第三阶段

- **可视化编辑器**：在地图上画路径、打时间关键帧，导出为数据文件（贡献者门槛大幅降低）。
- 社区贡献流程（Pull Request + 自动校验）。
- 导出 GIF/MP4，方便分享。
- 接入 OpenHistoricalMap 等外部数据。

## 6. 数据模型

### 6.1 存储方式

一场战役 = 一个目录，全部是人类可读、Git 友好的文本文件：

```
data/campaigns/normandy-1944/
├─ campaign.yaml      # 元数据、阵营、章节、镜头
├─ units.yaml         # 部队 + 各自的移动轨迹
├─ events.yaml        # 事件
├─ areas/*.geojson    # 随时间变化的控制区域/战线快照
└─ sources.yaml       # 参考文献（其他文件用 id 引用）
```

构建时用 JSON Schema / zod 校验，并合并为前端可直接加载的 JSON。

### 6.2 核心实体

| 实体             | 关键字段                                                                                                              |
| ---------------- | --------------------------------------------------------------------------------------------------------------------- |
| **Campaign**     | id, title{zh,en}, period{start,end,precision}, theatre, summary, sides[], chapters[], basemapHint, sources[]          |
| **Side**         | id, name, color, icon, 可选 flag/描述                                                                                 |
| **Unit**         | id, side, name{zh,en}, kind（步兵/装甲/舰队/骑兵…）, echelon（师/军/集团军…）, commander, strength[]（随时间）, track |
| **Track**        | interpolation（linear / along-path / sea-route）, waypoints[]                                                         |
| **Waypoint**     | t, pos[lng,lat], **timePrecision**, **confidence**, note, sources[]                                                   |
| **Event**        | id, t, pos, kind（战斗/登陆/围城/会议…）, title, body, units[], sources[], confidence                                 |
| **AreaSnapshot** | t, geometry(Polygon/MultiPolygon), side, kind（占领区/包围圈/攻势范围）, confidence                                   |
| **Arrow**        | from/to 折线或曲线, t 起止, side, kind（进攻/撤退/机动）                                                              |
| **Chapter**      | id, title, tStart, tEnd, timeScale, camera{center,zoom,pitch,bearing}, narration                                      |
| **Source**       | id, citation, url, kind（一手/二手）, license                                                                         |

### 6.3 时间与可信度（本项目的特色设计）

**时间**：使用 ISO 8601 扩展格式，公元前用天文纪年（公元前 216 年 = `-0215`，需在文档里明确规定并封装转换函数）。每个时间点带 `precision`：`minute | hour | day | month | season | year`。低精度的点在动画中以"时间段内模糊移动"的方式表现，而不是伪装成精确到分钟。

**历法**：1582 年前的日期标注所用历法（儒略/格里高利/中国传统历），内部统一转换为格里高利历储存，原始记载写进 `note`。

**可信度**（4 级，界面上有对应视觉编码）：

| 级别            | 含义             | 视觉                  |
| --------------- | ---------------- | --------------------- |
| `documented`    | 有直接史料记载   | 实线、实心图标        |
| `reconstructed` | 由史料合理还原   | 实线、图标带细边      |
| `approximate`   | 大致位置/时间    | 虚线、半透明          |
| `conjectural`   | 学界有争议或推测 | 点线 + 图例注明"推测" |

### 6.4 示例（示意坐标，仅用于说明结构）

```yaml
# units.yaml
- id: us-1st-inf-div
  side: allies
  name: { zh: 美军第1步兵师, en: 1st Infantry Division (US) }
  kind: infantry
  echelon: division
  track:
    interpolation: sea-route
    waypoints:
      - t: '1944-06-05T22:00'
        pos: [-1.30, 50.10]
        timePrecision: hour
        confidence: documented
        note: 由运输舰队搭载，驶向诺曼底
        sources: [ref-ch-of-mil-hist]
      - t: '1944-06-06T06:30'
        pos: [-0.87, 49.37]
        timePrecision: minute
        confidence: documented
        note: 奥马哈海滩（Easy Red / Fox Green 段）登陆
        sources: [ref-ch-of-mil-hist]
```

## 7. 时间与动画引擎设计

**核心思想：状态是时间的纯函数。**

```ts
getSnapshot(campaign: Campaign, t: number): {
  units:   { id; pos; heading; status; confidence }[];
  events:  { id; phase: 'upcoming' | 'active' | 'past' }[];
  areas:   GeoJSON.FeatureCollection;  // 当前时刻插值/阶跃后的区域
  arrows:  ...;
}
```

- 纯函数 → 好测试、拖时间轴无状态漂移、倒放/跳转零成本、URL 分享 `t` 即可复现。
- 渲染层每帧调用 `getSnapshot(t)`，更新地图图层，不在渲染里保存业务状态。
- **虚拟时钟**：`t` 由时钟对象推进，速度 = 每真实秒对应的历史时长；章节可覆盖倍速（平静期加速，激战期放慢）。
- **轨迹插值**：
  - `linear`：两点间大圆线性插值。
  - `along-path`：沿给定 GeoJSON 折线按弧长匀速（可缓动）。
  - `sea-route`：同上，预置航线避开陆地。
  - 时间精度低的路段，使用区间内非匀速分布并在 UI 提示。
- **区域变化**：相邻快照之间默认"阶跃"（诚实：史料通常只有快照），可选 morph 动画（仅当两快照拓扑一致）。
- **性能**：地图层用 GeoJSON source 增量更新；尾迹与大量单位时切换到 deck.gl TripsLayer。

## 8. 技术选型（推荐）

| 层       | 选择                                                    | 理由                                                                          |
| -------- | ------------------------------------------------------- | ----------------------------------------------------------------------------- |
| 构建     | Vite + TypeScript                                       | 快、类型安全，数据结构强依赖类型                                              |
| UI       | React                                                   | 生态最全（react-map-gl、deck.gl 官方绑定）【待确认：你是否偏好 Vue/Svelte？】 |
| 地图     | **MapLibre GL JS**                                      | 开源、无需商业 key、矢量渲染、支持 3D 地形与自定义样式                        |
| 动态图层 | deck.gl（TripsLayer / IconLayer / ArcLayer）            | 尾迹动画、大量图标高性能                                                      |
| 几何计算 | turf.js                                                 | along / lineSlice / bearing 等                                                |
| 军标     | milsymbol（现代战役，APP-6 军标）+ 自绘图标（古代）     | 现成 SVG 军标库；古代战役需自定义骑兵/战舰等图标                              |
| 状态     | zustand                                                 | 轻量，适合"时钟 + 选中项 + 图层开关"                                          |
| 校验     | zod（或 JSON Schema）                                   | 数据文件构建期校验                                                            |
| 底图瓦片 | Protomaps PMTiles（自托管静态文件）或 MapTiler 免费额度 | PMTiles 可纯静态部署、零后端                                                  |
| 测试     | Vitest（引擎单测）+ Playwright（冒烟 E2E）              | 引擎是纯函数，单测价值最高                                                    |
| 部署     | GitHub Pages 或 Cloudflare Pages                        | 纯静态，免费                                                                  |

**不做后端**（MVP）：数据在仓库里，构建期打包，避免运维和成本。如果以后要用户系统/投稿，再引入。

## 10. 内容生产与准确性策略

**每场战役的制作流程**：

1. 选题与范围界定（时间跨度、地理范围、要讲清的 3–5 个关键问题）。
2. 收集来源（优先：一手史料、官方战史、权威学术著作；地图优先公有领域，如美国陆军军事历史中心的战史地图）。
3. 整理时间线（先纯文本，再上地图）。
4. 录入数据，逐点标注 precision / confidence / sources。
5. 校验脚本：时间单调、速度合理性（部队移动速度超过阈值则告警）、坐标是否落在合理区域（如陆军单位不应在海中）。
6. 自审 + 他人审阅，附"已知争议"说明。

**规范**：

- 界面上每个数据点都能点开看到来源，没有来源的点不上线。
- 叙述用事实性语言，避免情绪化定性；有多种叙述立场时并列说明。
- 争议边界/地名：以当时称谓为主，并在必要处附现称。
- 图片、地图、底图的授权在 `sources.yaml` 里登记，只用公有领域或明确允许的素材。
- 使用外部历史数据集（如 Natural Earth、OpenHistoricalMap、historical-basemaps 等）前，**逐个核实许可证**再引入。

## 13. 主要风险

1. **内容工作量被低估**：每场战役数据研究可能远超开发时间。→ 先做 1 场做透，测出真实单场耗时，再定规模；尽早做编辑器。
2. **"动画精确感"误导**：→ 可信度视觉编码 + 低精度模糊表现是设计必需项，不是可选项。
3. **底图与历史不符**：→ 明确定位为"地形参照"，历史要素全用自有图层。
4. **版权与授权**：→ 素材入库前登记许可证，默认只用公有领域。
5. **范围膨胀**（3D、AI 生成内容、社区、视频……）：→ 严格按里程碑推进，M4 之前不碰第二阶段功能。
6. **叙述中立性**：→ 遵守 §10 规范并留出"争议说明"字段。

### 由决策产生的设计调整

- **四渡赤水的特点**：时间尺度为天（约 4 个月）而非分钟；部队沿山地与河谷行进，路线靠 `via` 折线贴合；对手（川军、黔军、滇军、中央军）立场与行为各异，因此设为独立阵营；许多对手只有战斗当日的零星记载，
  用部队的 `lifespan` 限定出现窗口，**不编造窗口之外的位置**。
- **底图**：四渡赤水的地形（山脉、赤水河、乌江）本身就是叙事的一部分，M2 需要带地形/水系的底图，并保证在中国大陆网络下可用。
  倾向：自托管 **PMTiles 区域切片**（川黔滇范围），不依赖境外瓦片服务；同时满足 GitHub Pages 与腾讯云两处部署。
- **部署迁移到腾讯云**：前端是纯静态文件，`VITE_BASE` 控制部署路径；用 hash 路由避免静态托管刷新 404。腾讯云可选 COS + CDN 或 Nginx。
  若绑定域名并使用大陆节点，需要完成 **ICP 备案**（这一步耗时，建议尽早启动）。
- **数据来源**：优先中文一手史料与权威战史；起草阶段以中文维基百科等二手资料为线索，凡未直接核对原书的条目标记为待核，
  不得在未核对时升级为 `reviewed`。
- **贡献流程**：PR 必须通过 CI（格式、lint、类型、数据校验、测试、构建）；数据 PR 须有非作者的审阅者后才能把 `status` 升为 `reviewed`。
